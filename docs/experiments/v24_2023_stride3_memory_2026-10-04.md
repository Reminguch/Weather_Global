# 2023 verification: forecasts every three days

This campaign evaluates the seven previously frozen policies on 122 starts at
00 UTC, every three days from January 1 through December 30, 2023. Each start
has 40 six-hour leads. This is a year-round sample, not all daily forecasts.
There is no new training and no cross-resolution comparison.

Campaign directory:
`artifacts/evaluations/v24_res1_2023_stride3_memory_20261004`.

The campaign is prepared for numerical qualification. **Preparation is not a
completed evaluation or authorization to bypass qualification.** No jobs were
submitted during implementation. The current session has no working GPU;
the previous campaign's baseline discrepancies therefore remain unresolved.

## Scientific contract

Checkpoint, run-configuration and normalization identities match the September
25 campaign. M1 (di16, faster Mamba, SWA500–2000) is the primary model; M2/M3
are descriptive comparisons. M1_reset resets both temporal states every step.
The native V22 policies C_carry, C_reset and R_reset retain their loaders and
rollout arithmetic.

Forecasts have zero initial memory and independent autoregressive feedback.
Required inputs/truth extend from December 31, 2022 at 18 UTC through January
9, 2024 at 00 UTC. DJF/MAM/JJA/SON contain 30/31/30/31 starts.

The primary endpoint is `100*(1-sum(M1 loss)/sum(GraphCast loss))`, pooling all
starts and leads before division. GraphCast loss is computed directly with
its original normalization and weights. The primary paired 95% interval must
exclude zero on the positive side to establish the primary improvement.

The four secondary confirmatory endpoints are M1-versus-GraphCast at 240h,
M1-versus-M1_reset, C_carry-versus-C_reset and C_carry-versus-R_reset. The last
three pool all leads and use percentage-point differences in GC-referenced
loss reduction. Their intervals form one simultaneous 95% family; secondary
confirmation additionally requires primary confirmation. C_reset-versus-
R_reset is descriptive. Existing V22 controls do not establish a separately
trained, capacity-matched memory benefit for M1.

The bootstrap uses 10,000 paired, non-wrapping draws, seed 20260916, and blocks
of five starts (12 elapsed days). Sensitivities use three/seven starts and
five starts within calendar quarters. All models and leads share each draw.
The report discloses whether claims survive these sensitivities.

Eight pilot dates were previously inspected: January/February/April/May/July/
August/October/November 15, 2023. The user reports no influence on selection.
The primary sample includes three of these: February 15, July 15 and November 15.
A predefined 119-start sensitivity masks these dates after drawing blocks
on the original regular 122-position grid. This does not undo prior exposure
or eliminate overlapping pilot forecast windows. Do not call 2023 untouched.

Variable diagnostics pool physical-unit squared errors before taking square
roots: cosine-latitude spatial weights and equal pressure-level weights.
Seasonal and variable scores are descriptive, including degradations. A
scientifically valid negative or inconclusive result completes the campaign.

## Preparation and provenance

`run_v24_2023_eval.py prepare --initialization-stride-days 3` creates a schema2
protocol. Daily schema1 campaigns remain supported. A protocol cannot be
overwritten; numerical/runtime changes require a new campaign directory.

The frozen protocol includes model/statistic hashes, source snapshot, package
versions, internal BF16 versus FP32 field/state conventions, date manifests,
prior exposure, endpoint definitions, and training-provenance audit. The
audit distinguishes source-store coverage from manifest split and eligible
complete-segment input/target envelopes. It records inherited warmup
checkpoints and normalization fitting attributes. These bounds do not claim
to replay the exact minibatches used by every optimizer update.

The bounded data preflight checks all chunk files, year boundaries and saved
staging verification records. Source parity is established at the available
December 31, 2022 overlap; it is not a seasonal source-parity study.

From the repository root, inspect the frozen campaign without GPU inference:

```bash
source scripts/graphcast_env.sh
EVAL_WORKFLOW="$PWD/artifacts/evaluations/v24_res1_2023_stride3_memory_20261004"
python scripts/experiments/run_v24_2023_eval.py verify --workflow "$EVAL_WORKFLOW"
```

## Numerical qualification before production

The previous four-date 2022 pilots disagreed in nominally identical GraphCast
baseline losses by roughly 3%. Neither averaging those baselines nor relaxing
the frozen `rtol=0.001, atol=1e-6` gate is a repair. Internal BF16 plus GPU
aggregation/compiler variability is a hypothesis, not an established cause.

The frozen `diagnose_v24_2023_numerics.py` utility runs only 2022 probes. It
records effective parameter/state/statistic/input/RNG fingerprints, truth
and forcing fingerprints, per-lead field digests, exact losses, process and
GPU identities. Run the following evidence matrix on allocated A100-80GB
GPUs using the frozen environment:

| Evidence | Required executions |
| --- | --- |
| Within-process repeatability | Each of seven policies, interleaved mode, two repeats in one invocation |
| Fresh-process repeatability | M1 in another Python process on the same physical GPU |
| Matching-GPU repeatability | M1 on a different physical GPU of the same kind and driver |
| Baseline isolation | M1 standalone mode, without residual forward calls |
| Development bridge | M1 bridge mode, all 32 saved development initializations |

The generic GPU wrapper accepts phase `numerics`, then the probe's arguments:

```bash
# This is a future submission command, not run during implementation.
sbatch scripts/experiments/v24_2023_eval_gpu.slurm numerics "$EVAL_WORKFLOW" \
  --model-id M1 --label primary_m1 --mode interleaved --repeats 2
```

To establish the same-GPU fresh-process comparison, run the second invocation
within the same GPU allocation as the first. Separate queued jobs do not
guarantee the same GPU. Conversely, a differently labelled invocation on the
same GPU does not establish cross-GPU repeatability. The qualifier checks UUIDs
and process identities rather than trusting labels.

Use the frozen source and protocol XLA settings for every probe. In an
allocated shell the equivalent entrypoint is:

```bash
export PYTHONPATH="$EVAL_WORKFLOW/source:$EVAL_WORKFLOW/source/third_party/graphcast"
export XLA_FLAGS="$(python -c 'import json,sys; print(json.load(open(sys.argv[1]))["numerics"]["xla_flags"])' "$EVAL_WORKFLOW/protocol.json")"
python "$EVAL_WORKFLOW/source/scripts/analyze_models/diagnose_v24_2023_numerics.py" \
  --workflow "$EVAL_WORKFLOW" --model-id M1 --label fresh_m1 \
  --mode interleaved --repeats 1
```

Assemble qualification by passing every completed probe file with a repeated
`--probe-json` argument to the frozen `v24_2023_qualification.py` utility.
Completed files have the suffix `.probe.json`; manifests and intermediate
files are excluded from that glob. With no probes the utility emits an
explicitly pending report. Qualification recomputes
checks from hashed artifacts; manually marking a check passed cannot release
production. Missing or failed evidence stops the campaign before 2023.

After a demonstrated numerical repair, record the 2022 development bridge;
do not overwrite the earlier development results. Changed implementation or
runtime settings must be frozen in a new campaign before qualification.

## Pilots, production and outputs

Once numerical qualification passes, run two independent four-date pilots
per policy: 14 tasks, array 0–13. The gate checks complete metrics, repeated
baseline/full losses, effective identities, GPU kind and resource margins.
The production run has eight interleaved date shards per policy:56 tasks,
array 0–55, each with 15 or 16 starts.

Resources begin at one A100 80 GB GPU, eight CPUs, 16 GiB host RAM and 62 minutes.
Fresh pilots must show peak host RAM below 80% and the projected largest shard
runtime with 25% headroom fitting the allocation. Resource changes require a
new frozen allocation/protocol. CPU validation/merge uses two CPUs, 4 GiB and
15 minutes. Arrays have no concurrency throttle.

Use `afterok` dependencies and `--kill-on-invalid-dep=yes` for:
repeated pilots → validation gate → production → merge. The workflow also
enforces these gates internally, including evidence-file hashes. Preserve
complete outputs and resubmit only missing or failed tasks. Completed files
cannot be overwritten.

The final report contains per-start exact losses and variable MSE, pooled
losses and RMSE, named endpoint intervals, claim-sensitivity tables, seasonal
diagnostics, and PDF/PNG figures. Reports are generated only from complete
matched coverage. No synthetic test outputs belong in the campaign report.
Intervals describe weather-sample uncertainty conditional on these fixed
checkpoints and 2023; they do not measure training-seed or between-year
variation, extreme-event skill, or spatial-structure preservation.
