# Res4 small GraphCast and GC-Mamba 200k experiment

Status: submitted on 2026-09-16.

## Question

At resolution 4, does a deliberately shallow mesh4/width512/two-processor-step
GraphCast continue to improve through 200,000 one-step updates, and does
stateful GC-Mamba benefit from substantially longer training or a larger
temporal inner width?

## Runs

| Run | Initialization | Optimizer updates | Losses per update | Purpose |
| --- | --- | ---: | ---: | --- |
| Vanilla GC, mesh4/w512/mp2 | Continue exact step-50k parameters | 200,000 total | 8 | Establish the trained spatial baseline |
| Segment GC, mesh4/w512/mp2 | Fresh, all parameters trainable | 200,000 | 48 | Control for chronological BPTT training |
| GC-Mamba di16/ds16/l1 | Fresh, all parameters trainable | 200,000 | 48 | Small temporal model |
| GC-Mamba di64/ds16/l1 | Fresh, all parameters trainable | 200,000 | 48 | Larger temporal-capacity test |

All runs use 2015-2021 training data, 2022 validation, resolution 4, mesh4,
width512, two processor message-passing steps, BF16, AdamW at `1e-4`, weight
decay `1e-4`, batch size 8, and seed 0. GC-Mamba uses length-30 chronological
segments, BPTT6, state carry, and a temporal block interleaved after each of the
two processor steps. The segment-GC control uses the identical chronological
segment loader and BPTT loss positions with its temporal backbone disabled.

The segment runs process six supervised forecast losses per batch lane and
optimizer update. Therefore segment update 33,334 is approximately exposure
matched to vanilla update 200,000: about 1.6 million supervised forecast
losses. The full 200,000-update segment trajectories additionally test whether
capacity scaling was previously hidden by too few optimizer updates. Report
results both by optimizer update and cumulative supervised forecast losses.

## Continuation caveat

The standard trainer restores the vanilla step-50k parameters but does not
save or restore Adam state. The continuation therefore restarts Adam and the
sampling RNG at global step 50,000. It is a parameter continuation, not a
bit-for-bit uninterrupted 200,000-update run. The original configuration is
preserved as `run_config_before_200k_continuation.json` before training starts.

## Checkpoints and decisions

Training checkpoints and periodic validation are recorded every 10,000
updates. The first comparison is the vanilla learning curve through 200,000.
For the segment runs, compare 30k and 40k as bounds around the 33,334-update
exposure match, then follow all three models through 200k updates.

After these one-step runs, use the same autoregressive training and fixed
ten-day evaluation protocol for vanilla and GC-Mamba. Only after that matched
comparison should the experiment add spatial-only and residual-Mamba correction
branches to the trained vanilla checkpoint.

The smoke array uses the same launcher and model shapes with a separate output
root under `artifacts/checkpoints/smoke/`, two updates, evaluation/checkpointing
every update, and a 1:02 walltime. The production array starts only if all
three smoke tasks succeed.

The first smoke array, `14018581`, failed during argument parsing because the
segment trainer had not been updated for three required `RunConfig` fields.
The parser now sets the unused segment-evaluation caps and temporal insertion
count explicitly; its targeted configuration test passes. The dependent
production array `14018590` was cancelled without running.

Replacement smoke `14018690` then passed data opening and finite-segment
validation before exposing a second interface mismatch: the shared segment
metadata/evaluation code now requires evaluation-subset settings. The Mamba
segment configuration now carries those settings, uses 16 fixed stratified
segments for periodic evaluation, and uses the full validation year for final
evaluation. Its dependent production job `14018695` was cancelled without
running. The jobs in the table are the current replacements.

Smoke `14018846` completed all three checkpoint/evaluation round trips, but it
also showed that forcing JAX's debugging `platform` allocator made a steady
BPTT update take roughly 35-51 seconds. The closest historical pilot used the
default allocator and averaged 0.374 seconds/update. The launchers now retain
JAX's default allocator. Vanilla job `14018578` and pending production array
`14018849` were cancelled before useful new checkpoints, and replacement job
IDs are recorded in the table above. The default-allocator performance smoke
is the final gate before the replacement production array can start.
